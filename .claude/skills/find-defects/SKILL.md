# find-defects

Notifier / UseCase / Interface / Repository / Service の実装を攻撃者視点で精査し、Critical欠陥のみを報告する。

---

## 引数

| 引数 | 例 | 説明 |
|---|---|---|
| `<adr-path>` | `docs/adr/foo/bar.md` | 設計書 |
| `<commit-hash>` | `b7bdd80` | レビュー対象コミット |

- 両方指定 → 設計書 + diff でレビュー
- どちらか一方 → 指定されたもののみ
- 両方なし → ユーザーに確認

---

## 実行手順

### 1. 対象コードの取得

`<commit-hash>` が指定されている場合:

```bash
git show <commit-hash>
```

`<adr-path>` が指定されている場合: Read で読み込む。

---

### 2. 5視点レビュー

対象層: Notifier / UseCase / Interface / Repository / Service

以下5視点で精査する。**確信のない指摘は含めない。Critical以外は無視する。**

---

#### 視点1: 非原子性・並行呼び出し

「読んで → 判断して → 書く」3ステップが非原子なケース:
- 予約・決済・キャンセル等の重要アクションがUI連打・並行実行で二重発火したとき、二重書き込み・二重決済が起きないか
- `await A(); await B();` の間に同じメソッドが再度呼ばれ、状態が不正にならないか

#### 視点2: 異常系・部分失敗の中途状態

多段処理（決済API → 予約API → ローカル更新）で途中ステップが失敗したとき:
- 前ステップの副作用（課金・フラグ・ストレージ書き込み）が残留し、不整合な状態が確定しないか
- try-catch の範囲が広すぎて意図しない例外を握りつぶしていないか

#### 視点3: サイレント成功・サイレント失敗

呼び出し元が失敗に気づけないケース:
- メソッドが内部で例外をキャッチして成功として返している箇所はないか
- `SuccessResult` を返しているが、実際の API 呼び出し・書き込みが行われていない状態が生まれないか

#### 視点4: TOCTOU（Time-of-Check-Time-of-Use）

確認と実行の間に状態が変わるケース:
- `if (canBook) { await payment(); book(); }` のように await 中に前提条件が変化する箇所はないか
- 在庫・価格・セッション・クーポン有効期限を確認後 await が挟まり、実行時には状態が陳腐化していないか

#### 視点5: 機密情報の平文露出（ストレージ・ログ・エラーメッセージ）

攻撃者が ADB アクセス・APK 逆コンパイル・通信傍受で機密情報を得られるケース:
- 認証トークン・パスワード・PII を SharedPreferences / 平文ファイルに保存し、SecureStorage を使っていない箇所はないか
- `print` / `debugPrint` / ロガーで認証トークン・レスポンスボディ全体・PII を出力している箇所はないか
- `FailureResult` の error 内容・Exception メッセージにサーバー内部情報・スタックトレース・機密値が含まれ、View に素通りしていないか
- DTO に token / password / secret フィールドが存在するにもかかわらず、toString() やログ出力でマスクされていないか

---

### 3. 出力ファイル決定

```bash
mkdir -p docs/find_defects
TODAY=$(date +%Y-%m-%d)
N=$(ls docs/find_defects/defects_${TODAY}_*.md 2>/dev/null | wc -l)
N=$((N + 1))
```

出力先: `docs/find_defects/defects_${TODAY}_${N}.md`

---

### 4. レポート出力

Critical 欠陥のみ書き出す。欠陥ゼロなら「欠陥なし」のみ記載。

```markdown
# 欠陥レポート

**対象コミット**: `{commit-hash}`（指定なしの場合は省略）
**対象 ADR**: `{adr-path}`（指定なしの場合は省略）
**実施日**: {YYYY-MM-DD}

---

### {番号}. {タイトル}【Critical】
**箇所**: `{ファイルパス}` ({行番号}行目)
{欠陥の説明}
**影響シーケンス:**
1. {ステップ}
**影響**: {具体的な影響}

**再現手順:**
{テストコードまたは動作確認手順 — Step 5 参照}

---

## 結論
Critical {N}件。
```

---

### 5. 再現手順の生成

各 Critical 欠陥に対して、以下の優先順位で再現手順を生成し、対応する欠陥セクションの `**再現手順:**` に追記する。

#### 優先順位

1. **テストコード（最優先）**: Notifier / UseCase / Repository / Service 層の欠陥で、既存のスタブや `ProviderContainer` を使ってユニットテストが書ける場合
2. **動作確認手順**: テストで再現困難な場合（UI フロー依存・外部 API のタイミング依存など）

#### テストコードを選ぶ基準

- 欠陥が同期的または `await` で再現できる
- スタブで入力値を完全制御できる（サーバーが null を返す、など）
- 既存テストファイルのパターンに倣って書ける

#### テストコードの形式

既存テストファイル（`test/` 配下）のスタブ・ProviderContainer 構築パターンを参照し、プロジェクトの規約に合わせて生成する。

全テストを **Given-When-Then 構文** で記述する。

```dart
test('{欠陥を再現する日本語説明}', () async {
  // Given（事前条件: 欠陥が発現する状態）

  // When（操作: 欠陥が含まれるメソッドを呼び出し）

  // Then（事後条件: 期待される正常動作 — 現状のコードでは通らない）
  expect(...);
});
```

例外が即時に発生する場合は When / Then を統合できる:

```dart
// When / Then（不変条件違反 → 例外）
expect(() => ..., throwsA(isA<Exception>()));
```

- テストは **現状のコードで失敗する** ことを確認できるよう書く（欠陥の存在を証明するテスト）
- `flutter test {テストファイルパス}` で実行できる形にする

#### 動作確認手順の形式

```markdown
1. {前提条件の設定}
2. {操作手順}
3. {観察すべき挙動}（現状の誤った挙動）
4. **期待値**: {正しくあるべき挙動}
```

---

## 禁止事項

- テストファイル以外のコード・設定ファイルへの書き込み・編集は行わない（`docs/find_defects/` への Write と `test/` 配下への Write のみ許可）
- 修正案・修正指示を書かない
- Critical 以外を出力しない
- 確信のない指摘を含めない
