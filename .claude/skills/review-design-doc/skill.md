# review-design-doc

`gen-design-doc` で生成したドキュメント一式を、**生成時の経緯・文脈を一切持たない採点役**としてレビューするスキル。

**目的:** 良い注文（発注）の最終確認。AIが実装時に「読み替え」ではなく「そのまま実行」できる解像度になっているかを検証する。

**前提:** このスキルは `gen-design-doc`  skill実行後に使用する。実装着手前の最終チェックとして位置づける。

---

## 重要: このスキルの読み込み方

このスキルを実行する際、**gen-design-doc の生成内容・設計経緯・ユーザーとの会話内容は参照しない**。
対象ドキュメントを「初めて見る第三者」として読むこと。これが採点役としての前提条件である。

---

## Phase 0: 引数チェック

`$ARGUMENTS` から `feature_id` を取得する。

**引数が空の場合**: 処理を止め、ユーザーに以下を伝える。

```
feature_id が指定されていません。以下の形式で実行してください:

/review-design-doc <feature_id>

例: /review-design-doc braze_push_notification
```

**ドキュメントの存在確認:**
- `docs/adr/{feature_id}/design_doc.md` が存在しない場合は処理を止め、`gen-design-doc` を先に実行するよう伝える。

---

## Phase 1: ドキュメント読み込み（並列実行）

以下を並列で読み込む:

- `docs/adr/{feature_id}/design_doc.md`
- `docs/adr/{feature_id}/index.md`
- 全フェーズの `overview.md`（index.md から全パスを収集して読む）
- 全タスクスケルトンファイル（index.md から全パスを収集して読む）

---

## Phase 2: 5つの観点でレビュー

以下の観点を順に評価する。**生成した側の意図は一切考慮せず、ドキュメントに書かれた内容のみで判断する**。

### 観点 1: 合格ラインの解像度（完了条件）

各タスクの完了条件を以下の基準で判定する:

| 判定 | 基準 |
|---|---|
| ✅ 具体的 | コマンド名・実行結果・画面表示など「外の証拠」で検証できる |
| ⚠️ 曖昧 | "正しく動作する"、"正常に表示される"など抽象的な形容詞が含まれる |
| ❌ 未定義 | 完了条件が記述されていない、または「着手時に記述」のまま |

### 観点 2: 失格ラインの定義（失格条件）

各タスクの失格条件を以下の基準で判定する:

| 判定 | 基準 |
|---|---|
| ✅ 定義済み | 「こうなっていたら不合格」という具体的な判定基準がある |
| ⚠️ 不十分 | 失格条件はあるが抽象的で判定できない |
| ❌ 未定義 | 失格条件が記述されていない |

### 観点 3: 検証手順の具体性

タスクに検証手順（またはテスト方針）がある場合、以下の基準で判定する:

| 判定 | 基準 |
|---|---|
| ✅ 外の証拠ベース | `flutter test`、ADBコマンド、実機確認手順など具体的な手順がある |
| ⚠️ 内的証拠のみ | "コードを確認する"、"ログを見る"など外部から検証しにくい手順のみ |
| ❌ 未定義 | 検証手順がない |

### 観点 4: スコープの抜け漏れ

design_doc.md を読んで以下を確認する:

- スコープ内に記載された内容がタスク分解に網羅されているか
- タスク同士の依存関係が正しい順序になっているか（先にAが必要なのにBが先に来ていないか）
- フェーズ境界が論理的か（前フェーズが完了しないと次フェーズを開始できない依存関係になっているか）

### 観点 5: リスクのカバレッジ

design_doc.md の「リスクと注意点」セクションを読んで以下を確認する:

- 記載されたリスクに対応するタスクまたは完了条件が存在するか
- 重大なリスク（セキュリティ・データ損失・ストア審査リジェクト）が対策なしで放置されていないか

### 観点 6: テスト計画の解像度

`docs/test/{feature_id}/test_plan.md` の存在と内容を確認する:

| 判定 | 基準 |
|---|---|
| ✅ 十分 | スタブ境界・テストファイル構成・ProviderContainer骨格が記述されている |
| ⚠️ 不十分 | test_plan.md は存在するがスタブ境界のみ／構成が空欄のまま |
| ❌ 未作成 | `docs/test/{feature_id}/test_plan.md` が存在しない |

各タスクスケルトンの `## テスト計画（3条件）` セクションについて:

| 判定 | 基準 |
|---|---|
| ✅ 設計済み | 対象レイヤー・テスト種別・事前条件・事後条件が記述されている |
| ⚠️ 部分的 | レイヤーは記述されているが3条件が空欄 |
| ❌ 未記述 | 「着手時に記述」のまま放置（スケルトン段階であれば許容） |

**注意:** タスクスケルトン段階（未着手）の `❌ 未記述` は正常。着手済みタスクで未記述の場合のみ問題として報告する。

## Phase 3: レポート生成

`docs/adr/{feature_id}/review_design_doc_report.md` にレポートを出力する。

### レポートテンプレート

```markdown
# {機能名} デザインドックレビューレポート

> 生成経緯を持たない採点役による第三者レビュー。
> **このレポートの全指摘を修正する必要はない。致命的な問題のみ対応し、「念のための指摘」は人間が判断して棄却すること。**

---

## サマリー

| 観点 | 評価 | 致命的な問題数 |
|---|---|---|
| 合格ラインの解像度（完了条件） | ✅ / ⚠️ / ❌ | N件 |
| 失格ラインの定義 | ✅ / ⚠️ / ❌ | N件 |
| 検証手順の具体性 | ✅ / ⚠️ / ❌ | N件 |
| スコープの抜け漏れ | ✅ / ⚠️ / ❌ | N件 |
| リスクのカバレッジ | ✅ / ⚠️ / ❌ | N件 |
| テスト計画の解像度 | ✅ / ⚠️ / ❌ | N件 |

**次のアクション:**
（致命的な問題のみ箇条書き。問題がなければ「実装着手可」と記載）

## 判定の根拠（採点役の視点）

このレビューは設計経緯を知らない第三者として実施した。
以下の質問に答えられないタスクを「合格ライン不十分」と判定している:

- 「完了とはどのコマンドを実行したとき？」
- 「その結果は何が出力されればOK？」
- 「逆に何が出力されたら失格？」
```

## 完了時の出力

レポート生成後、ユーザーに以下を伝える:

```
レビュー完了。

docs/adr/{feature_id}/review_design_doc_report.md にレポートを保存しました。

致命的な問題: N件

━━━ 次にすべきアクション ━━━

【Step 3: ✅ 完了】/review-design-doc {feature_id}
  → 採点役AIが合格ライン・失格ラインの解像度を検品

【Step 4: 今すぐ】review_design_doc_report.md を確認・修正する
  → 致命的な問題のみ対応し、念のための指摘は棄却する
  → 「どこまで修正するか」の判断がレビューの最終工程

【Step 5: 次に実行】docs/adr/{feature_id}/kickoff_prompts.md を開く
  → 最初のタスクのプロンプトをコピーして Claude Code に貼り付ける
  → 新しい session で実行することで、前後の文脈なくタスクに集中できる
```
