# fix-defects

find-defects が生成した欠陥レポートを受け取り、欠陥の妥当性判断・修正方針立案・コード修正を実施する。

**処理は2フェーズに分かれる:**

| フェーズ | 担当 | ステップ |
|---|---|---|
| 計画フェーズ | メインスレッド | Steps 1〜4（読み込み・分析・方針立案）|
| 実装フェーズ | fork | Steps 5〜7（修正・テスト・削除）|

Steps 1〜4 完了後、**ユーザーの承認を得てから** fork して実装フェーズに進む。

---

## 引数

| 引数 | 例 | 説明 |
|---|---|---|
| `<report-path>` | `docs/find_defects/defects_2026-10-21_1.md` | find-defects が生成した欠陥レポート |

---

## 実行手順

### 1. 対象の読み込み

以下を並列 Read する:

- `<report-path>` — 欠陥レポート
- レポートに記載された全ファイルパス（`lib/` 配下）
- レポートが参照する再現テストファイル（`test/` 配下、存在する場合）

---

### 2. 再現テストの実行

レポートに再現テストファイルへの参照がある場合、実行して**現状の失敗を確認**する。

```bash
flutter test <再現テストファイルパス>
```

結果の解釈:

| 結果 | 意味 |
|---|---|
| 失敗（expected） | 欠陥がコードに存在することを証明 → 後続手順で修正 |
| 通過 | 欠陥がすでに修正済み → 後続の妥当性判断で「不妥当（修正済み）」と記録 |

---

### 3. 妥当性判断 → レポート追記

各欠陥を以下の3区分で判断し、レポートの末尾に `## 妥当性` セクションを追記する。

#### 区分

| 区分 | 定義 |
|---|---|
| **Critical（修正対象）** | 現在のコードに欠陥が存在し、現実の呼び出しシーケンスで発生しうる |
| **技術的負債（修正対象）** | 現在のコードに欠陥が存在するが現実の呼び出しでは発生しない、または呼び出し元のない死にコード |
| **不妥当（スキップ）** | コード変更済み・誤検知 |

「技術的負債」も修正対象とする。放置すると将来の呼び出しで欠陥が再現し、また死にコードはコードベースの信頼性を損なう。

#### レポート追記フォーマット

```markdown
---

## 妥当性

### {番号}. {欠陥タイトル}
**判断**: Critical（修正対象）/ 技術的負債（修正対象）/ 不妥当（スキップ）
**根拠**: {現在のコードの該当箇所を示し、現実の発生経路 or 死にコードの根拠を記載}
```

---

### 4. 修正方針立案 → レポート追記

妥当性で「修正対象」と判断した欠陥のみ対象とし、レポートの末尾に `## 修正方針` セクションを追記する。

方針立案の前に `docs/adr/`・`architecture.md`・`coding_rule.md` を参照し、修正がアーキテクチャ規約に整合することを確認する。

**品質目標:**
- **保守性**: 変更理由が一箇所に集約
- **可読性**: メソッド名・変数名で意図が伝わる
- **変更容易性**: 依存が抽象（Interface）に向いている
- **テスト容易性**: 副作用がコンストラクタ注入で差し替え可能

最小限の変更（YAGNI 適用）— 欠陥修正に必要な変更のみ行う。

#### レポート追記フォーマット

```markdown
## 修正方針

### {番号}. {欠陥タイトル}（{区分}）
**変更ファイル**: `{path}`
**方針**: {何をどう変えるか}
**テスト更新**: 要 / 不要（理由）
```

---

### 4.5. ユーザー確認（計画フェーズの完了ゲート）

**ここで処理を中断し、ユーザーの承認を得る。** 承認なしに Step 5 以降へ進まない。

以下の文言のみ出力する（要約・説明の追加は禁止）:

```
妥当性・修正方針を立てたので{レポートパス}を確認して。
OKであれば修正を開始する。
変更・追加指示があれば知らせて
```

#### ユーザー応答ごとの分岐

| 応答 | 次のアクション |
|---|---|
| **OK / 承認** | Step 5 以降を fork に委譲して実行 |
| **妥当性への異議** | Step 3 に戻って再判断 → レポートの `## 妥当性` を更新 → 再び Step 4.5 |
| **修正方針への修正指示** | Step 4 に戻って方針を修正 → レポートの `## 修正方針` を更新 → 再び Step 4.5 |
| **その他の追加指示** | 指示内容に応じて該当ステップに戻る → 再び Step 4.5 |

---

### 5. コード修正（fork で実行）

ユーザー承認後、Steps 5〜7 を fork に委譲する。fork には以下を伝える:

- `<report-path>` — 妥当性・修正方針が追記済みのレポート
- 再現テストファイルパス（存在する場合）
- 「レポートの `## 修正方針` に従って実装し、再現テスト通過後に再現テストファイルを削除すること」

fork は修正方針に従いコードを修正する。方針と乖離した変更は行わない。

---

### 6. テスト更新・検証（fork で実行）

以下の順序で実施する:

1. 再現テストファイルを実行 → **全テスト通過を確認**（失敗する場合は Step 5 に戻る）
2. 関連する既存テストファイルを特定し、修正に合わせて更新する
3. `flutter test` で全テストが通過することを確認
4. `flutter analyze` で静的解析エラーがないことを確認

---

### 7. 再現テストファイルの削除（fork で実行）

再現テストは欠陥存在証明用の一時ファイル。全テスト通過後に削除する。

```bash
rm <再現テストファイルパス>
```

削除後、再度 `flutter test` を実行し残りのテストへの影響がないことを確認する。

---

## 禁止事項

| 禁止 | 理由 |
|---|---|
| Step 4.5 のユーザー承認なしに Step 5 以降へ進む | 手戻り・無駄なtoken消費の防止 |
| 不妥当（スキップ）と判断した欠陥の修正 | スコープ逸脱 |
| find-defects が指摘していない箇所の改善・リファクタ | スコープ逸脱（別途 `/simplify` 等で対応） |
| 修正方針の未記載状態でのコード編集 | レポートとコードの乖離防止 |
| ADR・アーキテクチャ規約に反する修正 | 設計一貫性破壊 |
| 再現テストが通過する前に再現テストファイルを削除 | 修正の検証前削除 |
| 強制アンラップ `!` の使用 | coding_rule.md 違反 |
