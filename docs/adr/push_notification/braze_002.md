# BRAZE-002 通知カテゴリの確定

## 内容

`booking_transaction`、`trip_preparation`、`trip_support`、`marketing_offer` の定義・初期値・変更可否・抑制条件を確定する

## 完了条件

カテゴリ定義表を関係者で承認する

> **注意**: このファイルの内容は `notification_categories.md` に統合済み。今後の参照・更新はそちらで行う。

---

## 採用方針

初期リリースは **4カテゴリ** に絞る。`local_info`（位置情報権限・現地データ）と `engagement`（レビュー・レコメンドデータ）は、それぞれの依存機能が揃った段階で追加する。

| カテゴリID | カテゴリ名 | 採用フェーズ |
|---|---|---|
| `booking_transaction` | 予約・決済 | Phase 1（初期リリース） |
| `trip_preparation` | 出発準備 | Phase 1（初期リリース） |
| `trip_support` | 旅行中サポート | Phase 1（初期リリース） |
| `marketing_offer` | お得情報・キャンペーン | Phase 1（初期リリース） |
| `local_info` | 周辺・現地情報 | Phase 2（位置情報機能追加後） |
| `engagement` | レビュー・履歴・次回提案 | Phase 2（レビュー機能追加後） |

## カテゴリ定義

### `booking_transaction`（予約・決済）

| 項目 | 値 |
|---|---|
| **目的** | 予約確定・決済完了・変更・キャンセルなど、取引上必須の通知 |
| **初期値** | ON |
| **ユーザー変更** | 不可（OS通知権限のみ） |
| **頻度上限** | イベント駆動・上限なし |
| **重複排除キー** | `booking_id + event_type` |
| **Androidチャンネル重要度** | HIGH |

**抑制条件**

| 条件 | 内容 |
|---|---|
| 通知権限OFF | OS権限がない場合は送信不可（制御不能） |
| キャンセル完了後 | キャンセル完了通知のみ送信し、以降の予約系通知を停止 |

**送信イベント**

| イベント | 起因 | タイミング | 送信目的 |
|---|---|---|---|
| `booking_confirmed` | ユーザー / サーバー | 予約確定直後 | 即時確定→アナリティクス、手動承認→Push通知トリガー候補 |
| `payment_completed` | サーバー | 決済成功後 | Push通知トリガー候補（非同期決済の場合） |
| `booking_cancelled_by_user` | ユーザー | ユーザー自身がキャンセル操作を完了した直後 | 属性更新（アプリ内UIで完結・Push不要） |
| `booking_cancelled_by_operator` | サーバー | 事業者・システム都合によるキャンセル発生時 | Push通知トリガー |

送信イベントの全てがPush通知につながるわけではない。詳細は `notification_categories.md` の「基本原則：イベント送信と通知手段の分離」を参照。`booking_cancelled` をユーザー都合・事業者都合で分離している理由も、起因によって送信目的と通知手段が異なるため。

### `trip_preparation`（出発準備）

| 項目 | 値 |
|---|---|
| **目的** | カレンダー登録案内・チェックイン・持ち物・出発前リマインド |
| **初期値** | ON |
| **ユーザー変更** | 可 |
| **頻度上限** | 旅行あたり3〜5件 |
| **重複排除キー** | `booking_id + reminder_type + scheduled_at` |
| **Androidチャンネル重要度** | DEFAULT |

**抑制条件**

| 条件 | 内容 |
|---|---|
| カレンダー登録済み | カレンダー登録案内を停止 |
| 出発済み | 出発日以降すべて停止 |
| キャンセル済み | 全予約関連ジョブを停止 |
| 深夜帯（22:00〜7:00） | ユーザーTZで判定し送信しない |

**送信イベント**

| イベント | タイミング |
|---|---|
| `calendar_register_prompt_shown` | 出発7日前・カレンダー未登録時 |
| `calendar_registered` | カレンダー登録完了後 |
| `checkin_completed` | チェックイン完了後 |
| `trip_starting_soon` | 出発前日 |

### `trip_support`（旅行中サポート）

| 項目 | 値 |
|---|---|
| **目的** | 出発・到着・日程・オフライン表示・緊急情報 |
| **初期値** | ON |
| **ユーザー変更** | 一部可（緊急情報は変更不可） |
| **頻度上限** | 1日2〜3件（緊急除く） |
| **重複排除キー** | `booking_id + event_key + day` |
| **Androidチャンネル重要度** | DEFAULT（緊急はHIGH） |

**抑制条件**

| 条件 | 内容 |
|---|---|
| 旅行期間外 | `travel_start_at` 前・`travel_end_at` から24時間後に自動停止 |
| キャンセル済み | 旅行中サポートを停止 |

**送信イベント**

| イベント | タイミング |
|---|---|
| `trip_started` | 出発日または初回チェックイン後 |
| `offline_mode_entered` | オフライン状態検知時（※下記補足参照） |
| `trip_completed` | `travel_end_at` 経過後または完了操作時 |

**`offline_mode_entered` の設計補足**

> **前提の問題**: デバイスがオフラインになると、Brazeへのイベント送信も Push通知の受信も両方できない。海外旅行で現地SIM・Wifiがない場合は特に顕著で、「オフラインになった瞬間にBrazeへ通知する」は技術的に不可能。

この制約を踏まえ、`offline_mode_entered` は以下の**2用途に限定**して扱う。

**用途1: アプリ内UIのトリガー（Push通知ではない）**

オフライン検知はアプリ内で完結させる。Push通知の代わりに、アプリ内バナーやダイアログでオフライン対応機能を案内する。

```
接続断を検知
  → アプリ内UI: 「オフライン中です。保存済みマップが使えます」
  → キャッシュデータ・オフラインマップへ自動切り替え
  → Brazeイベントはローカルキューに保存（送信保留）
接続復帰
  → ローカルキューのイベントをBrazeへ遅延送信（アナリティクス目的のみ）
```

**用途2: 予防的なPush通知（オンライン時に事前送信）**

オフライン中の案内は、**オフラインになる前**に届けるしかない。Brazeのキャンペーンで以下のようなタイミングで事前送信する。

| タイミング | 通知例 | 条件 |
|---|---|---|
| 出発前日（オンライン時） | 「現地でオフラインになっても大丈夫。マップをダウンロードしておきましょう」 | `offline_map_downloaded = false` |
| 旅行開始直後（オンライン時） | 「Wifiが繋がっているうちにオフラインマップを保存しておきましょう」 | `offline_map_downloaded = false` |

**結論: `offline_mode_entered` の実際の役割**

| 役割 | 実現方法 |
|---|---|
| オフライン中のUI案内 | Push通知ではなくアプリ内UI（バナー・ダイアログ） |
| オフライン体験のアナリティクス | 接続復帰後にBrazeへ遅延送信（どのユーザーがどれだけオフランになったか把握） |
| 予防的なオフライン対策の案内 | オンライン時に事前Push送信（出発前日・旅行開始直後） |

Push通知として直接オフライン中に届けることは**想定しない**。`offline_map_downloaded` を出発前に確認し、未ダウンロードならオンライン時に案内するのが実際の設計フロー。

### `marketing_offer`（お得情報・キャンペーン）

| 項目 | 値 |
|---|---|
| **目的** | 割引・次回予約促進・限定プラン |
| **初期値** | OFF |
| **ユーザー変更** | 可 |
| **頻度上限** | 週2件 |
| **重複排除キー** | `campaign_id + user_id` |
| **Androidチャンネル重要度** | LOW |

**抑制条件**

| 条件 | 内容 |
|---|---|
| マーケ同意未取得 | `marketing_consent = false` の場合は送信しない（OS権限とは独立して管理） |
| クールダウン中 | 直近7日以内に同カテゴリ送信済みの場合は抑制 |
| 直近予約者 | 予約確定〜出発前のユーザーへの重複施策を抑制 |

**同意フロー上の注意点**

- OS Push権限とは別に、アプリ内でマーケティング通知への明示同意（`marketing_consent`）を取得する
- Apple HIG・Brazeガイドラインに従い、オプトアウト手段を常に提供する
- iOSのネイティブ権限ダイアログは初回1回限りのため、価値が伝わるタイミング（予約後など）で要求する

## 承認にあたって関係者と認識合わせをすべき重要ポイント

### 1. `booking_transaction` の通知手段とユーザー変更可否

`booking_transaction` は全イベントをPush通知で届けることを前提としているが、**ユーザーが操作して同期的に完了するイベント**（即時決済・即時予約確定など）はアプリ内UIで完結でき、Push通知は不要。「ユーザー変更不可」の制約もPush通知にのみ適用されるため、同期完了イベントをアプリ内UIで扱う場合はこの制約自体が不要になる。

一方、**サーバー起因の非同期イベント**（手動承認型予約確定・非同期決済失敗・事業者都合のキャンセル・返金処理）はユーザーがアプリを閉じた後に発生するため、Push通知が必要になる。この場合の「ユーザー変更不可」は取引上の信頼性を担保するために正当な設計といえる。

| パターン | 具体例 | 通知手段 | ユーザー変更不可の適用 |
|---|---|---|---|
| 同期完了（ユーザー操作直後） | 即時決済成功・即時予約確定 | アプリ内UI | 不要 |
| 非同期・サーバー起因 | 手動承認確定・非同期決済失敗・事業者キャンセル・返金 | Push通知 | 適用 |

各イベントの同期・非同期はサーバー仕様次第のため、BRAZE-020 実装前に確認が必要。

**確認事項**: 各イベントが同期・非同期のどちらに該当するかをサーバーチームと確認し、Push通知が必要なイベントの範囲を確定できるか

---

### 2. `marketing_offer` はデフォルトOFF・OS権限とは別に同意が必要

マーケティング通知は初期値OFFで、OSのPush許可に加えてアプリ内同意（`marketing_consent`）を別途取得する設計にする。[Apple ヒューマンインターフェイスガイドライン](https://developer.apple.com/jp/design/human-interface-guidelines/managing-notifications)（通知の管理 > マーケティング通知の送信）およびBrazeガイドラインへの準拠が理由だが、マーケティングチームにとっては**初期配信リーチが大幅に制限される**ことを意味する。

**確認事項**: 初期値OFFおよび二重同意の方針を、マーケティング側の施策計画として受け入れられるか

---

### 3. オフライン中はPush通知を届けられない

デバイスがオフライン時はBrazeへのイベント送信も通知受信も不可能なため、`offline_mode_entered` のシナリオでPush通知による案内はできない。オフライン時の案内は**アプリ内UIで完結**し、Push通知は「オフラインになる前（オンライン時）」に事前送信する設計になる。

**確認事項**: 旅行中のオフラインサポートをPush通知ではなくアプリ内UIで担う設計方針を合意できるか

---

### 4. `local_info` と `engagement` はPhase 2に延期

位置情報機能・レビュー機能が揃っていないため初期リリースには含めない。この2カテゴリを後回しにすることで、旅行後のレビュー依頼や周辺スポット通知は**Phase 1では配信されない**。

**確認事項**: Phase 1でレビュー依頼・周辺情報通知がないことを、ビジネスおよびロードマップとして受け入れられるか

---

### 5. `trip_support` の「緊急情報」の定義が未確定

緊急情報はユーザー変更不可・HIGH優先度で送る設計だが、何を「緊急」とするか（フライト遅延・自然災害・運行停止 など）の判定基準が決まっていない。範囲を広げすぎると通知の信頼性が下がり、狭めすぎると本来案内すべき状況で届かない。

**確認事項**: 「緊急情報」として扱う事象の範囲とその判定基準（サーバー側・アプリ側・Braze側の誰が判定するか）を合意できるか

### 6. iOS / Android の権限ダイアログ仕様と要求タイミング

Push通知権限の挙動はOSによって異なる。いずれも「初回起動直後に無差別に要求すると拒否率が高くなる」点は共通であり、価値が伝わるタイミングまで遅らせる設計にする。

#### iOS

- 権限ダイアログは**原則1回限り**。拒否後はOS設定からしか有効化できない
- アプリを再インストールしない限り再プロンプトは不可
- Provisional Authorization（仮許可）を使えばダイアログなしで静かな通知を届けられるが、通常のアラート通知と同じに扱えないため用途と期待値を関係者で揃える必要がある

#### Android 13+

Android 13（API 33）以降では `POST_NOTIFICATIONS` ランタイム権限が必須となり、新規インストール時の通知は**デフォルトOFF**になった。

| 状況 | 挙動 |
|---|---|
| 新規インストール（Android 13+） | 通知はデフォルトOFF。アプリが明示的に権限を要求するまで通知不可 |
| 既存アプリのアップグレード（12L以下で通知ON → 13+へ） | 権限は自動付与される |
| 1回目の拒否 | `shouldShowRequestPermissionRationale()` が `true` を返す間は再プロンプト可能 |
| 2回目の拒否 | システムが永続的にブロック。アプリからの再プロンプト不可・OS設定からの有効化のみ |

iOSと異なり「1回目の拒否後に説明画面を挟んで再プロンプトできる」機会が1度だけある。ただし2回拒否されるとiOSと同様にOS設定への誘導しかできなくなる。

`AndroidManifest.xml` への権限宣言も必要。

```xml
<uses-permission android:name="android.permission.POST_NOTIFICATIONS"/>
```

#### 共通の設計方針

- アプリ起動直後ではなく、**予約完了後など通知の価値が伝わるタイミング**で要求する
- Androidの「1度目の拒否→説明→再プロンプト」の機会を活かすため、初回要求前にアプリ内で通知の目的を説明するUI（事前説明画面）を挟む設計が有効
- 権限拒否後はPushではなくアプリ内メッセージや設定画面への誘導に切り替える

**確認事項**: 権限要求のタイミング・事前説明UIの設計をPM・マーケティングと合意できるか（BRAZE-005 で詳細設計）

### 7. 通知本文に機微情報を含めない

予約番号全文・決済金額・クレジットカード情報・住所などはロック画面に表示しない設計にする。通知文面のデザイン段階でこの制約を共有しておかないと、後から文面の修正コストが発生する。

[Apple ヒューマンインターフェイスガイドライン](https://developer.apple.com/jp/design/human-interface-guidelines/notifications)（通知 > ベストプラクティス）への準拠（下記引用）

> 取り扱いに注意を要する情報、個人情報、機密情報は通知に含めない。ユーザが通知を受け取った時点で何をしているかは予想できません。ほかの人に見られるおそれもあるため、プライベートな情報を含めないことが重要です。

**確認事項**: 通知文面に機微情報を含めない制約を、コピーライティング・デザイン担当と事前共有できているか
